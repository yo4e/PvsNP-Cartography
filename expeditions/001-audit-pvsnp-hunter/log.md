### Preliminary finding A — minimum_approx_degree does not search minimum approximate degree

In the current source, `PolynomialApproximator.minimum_approx_degree()` immediately discards the `error` parameter:

```python
del error
```

It then returns function-specific closed-form heuristics, e.g.:

- parity / xor: `n` over GF(2), roughly `n/2` over GF(3)
- majority: roughly `sqrt(n)`, with a parity adjustment over GF(3)
- PHP: roughly `0.6 n`, with a field-dependent adjustment

The method does **not** call `_can_approximate()`.

Therefore values generated through this path are not established by the code as exact minima of a 1/3-approximation search.

### Preliminary finding B — n > 8 values are extrapolated

For non-graph functions, `DegreeComplexityEstimator._estimate_for_field()` uses `minimum_approx_degree()` only at n=6,7,8 and extrapolates beyond n=8 with a linear growth increment.

Thus the published n≤15 tables for PHP and Majority are, at least for n>8, deterministic extrapolations from heuristic seed formulas, not exhaustive finite-n approximation-degree calculations.

### Preliminary finding C — graph functions compute a different quantity

For CLIQUE and Independent Set, the estimator takes a different path:

`graph_function_degree()`

It evaluates the Boolean graph property on all graphs for a small vertex count, applies a finite-field Möbius transform, and returns the highest-degree nonzero multilinear coefficient.

That is the **exact degree of the represented Boolean function as a multilinear polynomial over GF(p)** for those small instances.

It is not automatically the same object as minimum 1/3-approximate degree.

### Preliminary finding D — output labels blur the distinction

The lower-bound result uses labels such as:

`bound_type="approximate_polynomial_degree"`

and prose such as:

> Computed minimum degree 1/3-approximation over GF(2), GF(3)

This wording appears stronger than what the implementation establishes for the non-graph paths.

### Preliminary finding E — formal layer is currently scaffolding

The inspected Lean file includes major lower-bound landmarks as axioms and several target propositions whose body is effectively:

This is explicitly marked with TODO comments in the source, so it should be treated as scaffolding rather than a formal proof of the named lower bounds.

### Reproduction A — PHP table and fitted exponents reproduce exactly

An independent transcription of the current formula/extrapolation logic reproduces the published PHP table for n=2..15 exactly, including:

- GF(2) power-fit exponent: `0.9533698286984779`
- GF(3) power-fit exponent: `1.2079016267666487`

This is a successful software-output reproduction, but it changes the interpretation of the result.

For PHP, the seed formula is:

```text
min(n, max(2, floor(0.6 n) + [p=3 and n>=7]))
```

For n>8 the estimator does not evaluate PHP at all. It computes a slope from n=6,7,8 and extrapolates.

The reported cross-field pattern is therefore generated by the formula itself. At the extrapolation boundary:

```text
GF(2): d6=3, d7=4, d8=4 -> growth=1
GF(3): d6=3, d7=5, d8=5 -> growth=2
```

The larger GF(3) fitted exponent is consequently not an empirical discovery about a PHP Boolean encoding. It is a numerical consequence of a hand-coded field adjustment followed by the extrapolator, until the `min(n, ...)` cap is reached.

### Reproduction B — graph table independently reproduces as exact algebraic degree

A separate graph enumerator plus finite-field Möbius transform reproduces the published CLIQUE and Independent Set rows exactly:

| edge variables | vertices | GF(2) | GF(3) |
|---:|---:|---:|---:|
| 3 | 3 | 3 | 3 |
| 6 | 4 | 6 | 6 |
| 10 | 5 | 9 | 10 |
| 15 | 6 | 15 | 14 |

The implemented predicate is not a free CLIQUE(k) parameter. For a graph on `v` vertices it asks whether there is a clique, or independent set, of size at least `ceil(v/2)` (with a minimum threshold of 2).

For that implemented predicate, these rows are genuinely exact degrees of the unique multilinear representation over GF(p). They are still not minimum 1/3-approximate degrees merely by virtue of being exact algebraic degrees.

### Attack F — exact tiny-instance checker refutes the “minimum 1/3” label

The target repository contains an unused helper `_can_approximate()`. It classifies an assignment as 1 iff a GF(p) polynomial is nonzero and measures the fraction of Boolean-cube assignments misclassified.

The audit harness implements the same prediction/error semantics, but unlike the target helper it enumerates **all** multilinear monomials of degree at most d rather than truncating the candidate basis to `n+3` monomials. It searches degrees in ascending order, so the first witness is exact for this explicitly stated finite optimization problem.

Selected comparisons:

| function | n | field | reported | exact audit degree |
|---|---:|---|---:|---:|
| parity | 2 | GF(2) | 2 | 1 |
| parity | 3 | GF(2) | 3 | 1 |
| parity | 4 | GF(2) | 4 | 1 |
| parity | 4 | GF(3) | 2 | 1 |
| majority | 2 | GF(2) | 1 | 0 |
| majority | 3 | GF(3) | 2 | 1 |
| majority | 4 | GF(2) | 2 | 0 |
| majority | 4 | GF(3) | 2 | 0 |

The parity/GF(2) contradiction is especially direct: `x1 + ... + xn (mod 2)` computes parity exactly and has degree 1. Therefore a reported “minimum approximation degree” of n cannot be correct for any approximation notion in which exact GF(2) representation is an admissible approximant.

The majority n=4 zero-degree result also exposes a weakness of the helper's average-error semantics: the constant-zero classifier makes only 5 errors among 16 assignments, which is `5/16 < 1/3`. That quantity should not be silently conflated with a standard worst-case/pointwise approximation-degree notion.

### Attack G — PHP has no degree-analysis encoding

The polynomial-degree path never constructs a PHP truth table. `minimum_approx_degree("php", ...)` receives only the string name, n, and p and returns the formula above.

Moreover, the generic `_truth_table()` helper has explicit branches only for parity/xor, majority, and a toy `clique = all(bits)` predicate. Its fallback is:

```python
int(sum(bits) == 0)
```

So even if the currently unused search helper were wired to `"php"` without further changes, it would analyze NOR, not the pigeonhole principle.

The repository does contain a separate SAT-oracle PHP CNF generator. The degree estimator does not consume that encoding.

### Attack H — the dormant search helper is itself not exhaustive

`_can_approximate()` builds all degree-d monomials and then immediately restricts the coefficient search to:

```python
selected = monomials[: min(len(monomials), n + 3)]
```

Thus it cannot certify a minimum over all degree-d polynomials once more than `n+3` monomials exist.

This is independent of the more basic fact that `minimum_approx_degree()` never calls it.

### Primary-source terminology check

Smolensky's 1987 STOC paper uses low-degree polynomial approximation as a tool for lower bounds on bounded-depth circuits with MOD_p gates. In the paper's approximation lemma, low-degree polynomial functions are constructed that disagree with an operation/circuit on only a controlled fraction of assignments. The theorem-to-lower-bound chain has explicit circuit, field, depth, size, and error obligations.

Primary source:

Roman Smolensky, *Algebraic methods in the theory of lower bounds for Boolean circuit complexity*, STOC 1987, DOI `10.1145/28395.28404`.

Nothing in the audited code implements such a transfer theorem from the reported PHP sequence to an ACC0[p] lower bound. The public findings acknowledge that a theorem-level transfer is missing; the audit sharpens the problem by showing that the input “degree” sequence is itself synthetic rather than computed from PHP.
